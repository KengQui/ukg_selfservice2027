# Earning and Deduction Reference Library: PRD Context (Child)

Source: Product Design meeting recordings, 9 Oct 2026 and 16 Oct 2026 (auto-generated transcripts; names and terms may be mis-transcribed). Status:
Discovery / concept. Not yet prototyped in engineering. A Replit prototype exists for design only.

## Problem

Self-implementation customers must configure every earning and deduction code their pay register uses before payroll can run. Today:

There is no single source of truth for how earning and deduction codes should be set up in Ready. The team checks model companies by hand.
Configuration depends on conditions that a pay register does not show. For example, whether a mileage reimbursement is under an accountable
plan and therefore non-taxable. Implementation consultants know these conditions from experience. Self-service customers have no one to ask.
Naively scraping a pay register is not enough. The system needs follow-up questions to set up codes correctly.
Any AI used must not invent facts or act as a tax or benefits advisor.

## Goal

Build a curated, classified reference library of earning and deduction codes. The library drives:

1. Deterministic matching of a customer's extracted codes to known codes.
2. Known configuration conditions and questions for codes that cannot be matched or fully configured.
3. Plain-language questions, generated by AI from library content, that gather the missing information.
4. A recommended setup that the customer reviews and confirms.

Non-goal (current): Recommending a set of codes by company vertical. Most companies already have codes tied to their accounting system and cannot
change them.

## Core concepts (glossary)

Earning: Compensation paid to the employee (salary, bonus, overtime, allowance).
Deduction: Amount withheld or recovered from the employee (benefits, retirement contributions, tax withholding).
Ready roll-up type: The Ready category a code maps to.
Employee / employer portion: Whether the code has an employee contribution, an employer contribution, or both. If a portion exists and is not
set up, a separate code must be created later. This is a Ready restriction.
Configuration condition: A fact about the company that changes the setup of a code (for example, mileage calculation method).
Clarification question: The question the library defines to resolve an unknown condition.
Decision point: The recommended setup once conditions are known.
Deferred question: A question the user or implementation team cannot answer now. It goes to the implementation team's page.
Negative earning: A reversal recorded as earning in the source system. Ready records it as a deduction.
Imputed earning: Taxable benefit imputed to the employee. Created as a deduction in another system and as an earning in Ready. The team
still needs to resolve this.
Memo code: A code from a legacy vendor (for example, ADP) that gets created as an earning or deduction code. Open.

## Process flow

### Build time (one-time, then maintained)

1. Seed codes and facts from the existing earning/deduction recommendation tool.
2. Collect sources for conditions: IRS material, internal documents, and the source material behind the Ready Share triage advisor (owner to be
confirmed).
3. Round 1: extract conditions and questions from sources.
4. Round 2: implementation team reviews complex codes (for example, group term life, imputed earnings).
5. Payroll team confirms the schema covers everything Ready must track.
6. Maintain as new codes appear. Ownership is unresolved.

### Run time (per customer upload)

1. Upload the pay register (one EIN at a time).
2. Extract earning and deduction codes from the register. AI is used for extraction.
3. Match (deterministic): match each code to the library by name and aliases. - Matched codes are marked "ready for setup". They are not asked
about, but the user can review them at the end.
4. Check conditions: for each unmatched or partly known code, look up its conditions in the library. If the answer is in the extracted data, use it.
5. Ask (AI-assisted): for each missing condition, show a question card. The library's question text is rewritten in plain language by AI. Tax and
benefit questions ask the user to confirm.
6. Follow up: each answer triggers the library's follow-up questions, which may branch.
7. Configure: answers set up the code using the library's decision point. Anything the user cannot answer is deferred.
8. Defer: deferred items roll up to an implementation-team page, with answers keyed in and then applied to the system.
9. Optimize: suggest combining overtime codes (using cost centers), splitting bonuses, and removing unused codes.
10. Weighted-average overtime: ask the five standard questions from the payroll team. Each "yes" leads to an include or exclude confirmation.
11. Final review: all codes, mapped and configured, are shown for a last check before setup completes.

### AI role

Deterministic first. Matching, classification, and facts do not use AI.
AI is called only to: (a) phrase a question, (b) choose a follow-up when the answer is not deterministic, (c) explain an unknown or ambiguous code.
Not an agent experience. The user is not in an open conversation with AI. The flow is a wizard with occasional AI calls.
Previous payroll agents (milestones 1–3) are not expected to be reused. Effort needs re-evaluation.

## Business rules

1. Negative earnings (for example, a bonus reversal recorded as earning) are set up as deductions. Ready classifies by business purpose:
compensation goes in earning, employee holdings and recoveries go in deduction. Self-implementation users cannot override this. They must
confirm. Whether the implementation team can override is unknown.
2. Imputed earnings are created as earnings in Ready, while the other system creates them as deductions. Needs confirmation.
3. Employee or employer portion that is not set up forces a follow-up. This is a Ready restriction, not a government rule.
4. Multiple EINs: set up one at a time. After the first is configured, offer to copy its settings to the others. Copy is only possible once the target EIN
exists.
5. Tax and benefits: the system never gives advice. Questions ask the user to confirm treatment, and the result is flagged "tax to be verified" until
confirmed.
6. Facts over AI: the AI cannot override a library fact.

## Open questions

1. Storage and retrieval: database, RAG, or a hybrid. The team has not decided.
2. Maintenance and ownership: who updates the library as new codes appear?
3. Volume: about 500 codes, many questions each. Is this maintainable in the back end?
4. Source of conditions: does the triage advisor's source material work as the seed?
5. Analytics data: can historical company data from the analytics team support suggestions?
6. Implementation override: can the implementation team change a negative-earning setup for a customer?
7. Operational change path: how does an existing customer add a code or a new EIN after go-live?
8. Memo codes from legacy vendors (ADP): how are they represented?
9. Scale expectation: small companies use 5–6 codes; complex companies 50–60. What is the target?
10. Engineering approach: whether the library, questions, and decision logic belong to a separate team (Aman and Amit) or to the payroll team.

## Risks

Hallucination if AI generates facts instead of phrasing library content.
Scope overload: the library is a large project. The POC has to prove the concept first.
Tax liability if the system implies tax advice.
Maintenance burden as codes change.
Usability: users with no payroll knowledge may find the six-category review overwhelming.
Reuse: previously shipped payroll agents are not expected to be reused, which affects effort estimates.
Stakeholder alignment: this differs from the milestones 1–3 approach. Leadership alignment is needed before build.
